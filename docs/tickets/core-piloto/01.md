## What to build

Aplicação acessível com saúde/prontidão verificáveis, contrato HTTP, configuração validada, logs saneados e CI com fronteiras arquiteturais; substituir o scaffold necessário a esse percurso.

Esta é a fatia 01 do core aprovado. Aplicam-se as regras transversais da especificação principal; não há autorização para dados reais ou contratação implícita.

## Acceptance criteria

- [ ] Uma página Start consulta a API NestJS e apresenta o resultado de uma consulta sintética ao PostgreSQL, com contrato tipado e validação de entrada/saída.
- [ ] Liveness responde sem banco; readiness verifica PostgreSQL por adapter público com timeout, retornando indisponibilidade sem expor topologia ou credenciais.
- [ ] Fixar versões compatíveis e lockfile; preservar pnpm/Turbo e pacotes com exports explícitos, TypeScript estrito e domínio/aplicação sem frameworks. Não criar módulos futuros vazios.
- [ ] Configuração é validada no boot; Compose e migrações locais reproduzem o percurso somente com dados sintéticos. Logs JSON têm correlação e saneamento testado.
- [ ] CI executa geração, formato/lint, arquitetura/typecheck, unidades, integração PostgreSQL com migrações, build e E2E do percurso; um import proibido inserido como fixture negativa faz o check arquitetural falhar.
- [ ] Comprovar pelo percurso público e banco real a resposta saudável, a falha do banco e a ausência de código/configuração backend no bundle cliente. Registrar decisões de versões e limites ainda não implementados, sem declarar o produto pronto.
- [ ] Entrega demonstrável/verificável pela fronteira pública: persistência, API, interface aplicável e testes comportamentais, com isolamento, autorização e auditoria desde o recurso entregue.
- [ ] Seguir arquitetura e referências de UI do PRD/spec quando aplicáveis; documentar checks realmente executados e pendências, sem substituir integração real por mocks ou declarar passos não realizados.
