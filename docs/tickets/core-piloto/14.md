## What to build

Registro idempotente, protocolo, classificação de restrição e consulta limitada do autor, ainda sem acompanhamento obrigatório.

Esta é a fatia 14 do core aprovado. Aplicam-se as regras transversais da especificação principal; não há autorização para dados reais ou contratação implícita.

## Acceptance criteria

- [ ] Registrar estudante(s), data/hora, categoria, descrição, prioridade e providência imediata, com contexto opcional e autor autenticado; validar campos obrigatórios no servidor.
- [ ] Protocolo é único por escola/ano com ID opaco; duplo clique e repetição de rede produzem um único registro.
- [ ] Registro pode permanecer sem acompanhamento; autor recebe protocolo e próximo passo e consulta apenas seu envio e retorno operacional autorizado.
- [ ] Autor pode aumentar proteção; não remove restrição de categoria sensível. Restringir recebimento quando configuração escolar não permite triagem restrita.
- [ ] Página, API e PostgreSQL comprovam idempotência, autoria não forjável, restrição, isolamento e ausência de persistência sensível no navegador.
- [ ] Entrega demonstrável/verificável pela fronteira pública: persistência, API, interface aplicável e testes comportamentais, com isolamento, autorização e auditoria desde o recurso entregue.
- [ ] Seguir arquitetura e referências de UI do PRD/spec quando aplicáveis; documentar checks realmente executados e pendências, sem substituir integração real por mocks ou declarar passos não realizados.
